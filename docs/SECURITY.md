# LegacyGuard Security Design

## Reporting a vulnerability

Do not disclose a suspected vulnerability, exploit, sensitive log, secret, or
personal information in a public issue or discussion.

Use **Report a vulnerability** on the repository's **Security** tab when that
option is available. The repository is currently private while its permanent
location is unresolved, so that option may not be visible to every reporter. If
it is unavailable, use the maintainer's public GitHub profile only to request a
private reporting channel; do not include technical vulnerability details,
proof-of-concept code, secrets, or personal information in the initial public
message. A permanent private reporting route will be documented before public
visibility is enabled.

Include the affected version, a concise impact statement, safe reproduction
steps, and suggested remediation when possible. Use synthetic data and allow a
reasonable period for validation and coordinated remediation before public
disclosure. The project will acknowledge receipt, investigate in good faith,
and avoid requesting real user data as evidence.

## Authentication Design
LegacyGuard uses a JWT-based authentication model with a server-side session registry. Access tokens are short-lived, refresh tokens are longer-lived, and sessions can be revoked individually or across all devices.

## Encryption Approach
Sensitive future data should be encrypted before persistence. The backend includes a dedicated Fernet-based encryption service and configuration-based key handling so that later asset, beneficiary, and document data can be stored safely.

`ENCRYPTION_KEY` must be a valid Fernet key generated by `cryptography.fernet.Fernet.generate_key()`. The application validates the key at startup and fails fast with a configuration error if the key is missing or invalid. The service no longer pads or truncates keys. Development may load the key from `.env`; production should load the key from a secrets manager or KMS-backed configuration and must never commit key material to source control.

## Session Management
Sessions are tracked with metadata such as token identifier, creation time, expiration time, revocation state, and device information. This allows the system to revoke sessions and support future logout-from-all-devices workflows.

## Token Lifecycle and Expiration Policy
Authentication uses JWTs paired with a server-side session record. Each login creates one unique session token identifier (`jti`) stored in the session registry. Access and refresh tokens issued for that login share the same session identifier so logout and session revocation invalidate the whole session.

- Access tokens expire after `ACCESS_TOKEN_EXPIRE_MINUTES` minutes. The default development policy is 15 minutes.
- Refresh tokens expire after `REFRESH_TOKEN_EXPIRE_DAYS` days. The default development policy is 7 days.
- Database sessions expire after `REFRESH_TOKEN_EXPIRE_DAYS` days unless revoked earlier.
- Static JWT identifiers are not allowed; missing token identifiers are generated as UUIDs.
- Protected API routes accept access tokens only. Refresh tokens are longer-lived credentials reserved for refresh workflows.

Authentication errors for invalid, inactive, expired, or malformed token subjects are intentionally generic to avoid leaking account state.

## CORS Policy
Browser access is restricted through an environment-configured CORS allowlist. Wildcard origins are not allowed because credentials are supported for authenticated browser requests.

- Development allows explicit local frontend origins such as `http://localhost:5173`, `http://127.0.0.1:5173`, `http://localhost:3000`, and `http://127.0.0.1:3000`.
- Production requires explicitly configured trusted origins through `CORS_ALLOWED_ORIGINS`.
- `Access-Control-Allow-Credentials` is only used with explicit allowed origins, never with `*`.
- Allowed browser methods are limited to standard API methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, and `OPTIONS`.
- Allowed browser headers are limited to `Authorization` and `Content-Type`.

## Threat Model
Main concerns include:
- credential theft
- brute-force login attacks
- session hijacking
- unauthorized data access
- insufficient audit coverage

## Future Security Improvements
- MFA with TOTP and recovery codes
- rate limiting at the edge
- IP-based anomaly detection
- real encryption-at-rest for sensitive payloads
- admin support workflows and stricter RBAC enforcement
